# Reglas duras — security-master

| Regla | Verificación | Script o ruta | Qué previene |
|-------|-------------|---------------|--------------|
| Ningún secreto hardcodeado en el código; deben vivir en variables de entorno o vault | script | `gitleaks` / `TruffleHog` en pre-commit y CI (herramientas explícitamente listadas en la skill); verificado por `templates/check-gitleaks-configured.mjs` | credenciales filtradas al repositorio, visibles para siempre en el historial de git |
| Todo input de usuario se valida server-side; consultas SQL siempre parametrizadas, nunca por concatenación de strings | script (SAST) | Semgrep con reglas de inyección SQL (`javascript.lang.security.audit.sqli...` y equivalentes por lenguaje); verificado por `templates/check-semgrep-sqli-configured.mjs` | SQL injection — la vulnerabilidad A05 (Injection) del OWASP Top 10 |
| Nunca `eval()` ni ejecución de código dinámico sobre input de usuario | linter | `no-eval` (ESLint core) + `eslint-plugin-security` regla `security/detect-eval-with-expression` | ejecución de código arbitrario inyectado por el usuario |
| Nunca `os.system()` / `subprocess(shell=True)` / concatenación de comandos de shell con input externo | linter | `eslint-plugin-security` regla `security/detect-child-process`; equivalente Python: revisión de `subprocess(shell=True)` | command injection |
| Contraseñas nunca con MD5/SHA1/SHA256 crudo; hashing con Argon2id o bcrypt (cost ≥ 12) | linter | regla custom sobre `no-restricted-syntax` que prohíbe `crypto.createHash('md5'\|'sha1'\|'sha256')` en contexto de password | contraseñas reversibles o crackeables por fuerza bruta en caso de fuga de la base |
| Dependencias con vulnerabilidades conocidas bloquean el build | script | `npm audit --audit-level=high` / Dependabot / Snyk en CI; verificado por `templates/check-dependency-audit-configured.mjs` | vulnerabilidades de la cadena de suministro (A03 del OWASP Top 10) llegando a producción sin que nadie las vea |
| Fail-closed en toda comprobación de permisos: un error en la verificación deniega, nunca autoriza | no automatizable | — distinguir "este catch debe devolver `false`" de un catch legítimo que sí puede devolver `true` exige leer la lógica de negocio | un fallo transitorio (timeout, excepción) abriendo acceso que debía estar denegado (A10:2025) |
| Las respuestas de error nunca exponen stack traces, rutas internas ni errores de base de datos al usuario | no automatizable | — requiere revisar cada `catch`/`errorHandler` del proyecto; un grep genérico produce demasiados falsos positivos | reconocimiento de la infraestructura interna por parte de un atacante |
| Autorización verificada en cada request, no sólo en el login (deny by default) | no automatizable | — depende de la convención de rutas/guards de cada framework; requiere revisión por proyecto | escalación de privilegios, acceso a recursos de otro usuario (IDOR) |
| CSP y cabeceras de seguridad (`X-Content-Type-Options`, `X-Frame-Options`, HSTS) configuradas en producción | script | lectura de la configuración de headers del proyecto (`nuxt.config.ts` / middleware equivalente), falla si faltan las cabeceras mínimas; verificado por `templates/check-security-headers-configured.mjs` | XSS reflejado, clickjacking, MIME sniffing |
