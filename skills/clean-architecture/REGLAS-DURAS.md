# Reglas duras — clean-architecture

| Regla | Verificación | Script o ruta | Qué previene |
|-------|-------------|---------------|--------------|
| Los source code dependencies siempre apuntan hacia adentro; un círculo interior nunca importa nombres de un círculo exterior | script | `dependency-cruiser` con reglas de "forbidden" entre `domain/` → `application/` → `infrastructure/`/`frameworks/`; verificado por `templates/check-dependency-rule-inward.mjs` | que el dominio termine acoplado a detalles de infraestructura, imposibilitando cambiarlos sin tocar la lógica de negocio |
| Las Entities (reglas de negocio empresariales) no importan ningún framework, ORM ni librería de UI/HTTP | script | `dependency-cruiser`: regla que prohíbe imports de `express`/`@nestjs/*`/`typeorm`/`prisma`/etc. desde `src/domain/**`; verificado por `templates/check-domain-no-framework-imports.mjs` | reglas de negocio críticas que dejan de poder testearse sin levantar el framework |
| Los Use Cases reciben y devuelven DTOs/Request-Response models, nunca objetos del framework (`Request`/`Response`, entidades de ORM) | script | grep/`dependency-cruiser`: ningún archivo en `use-cases/`/`application/` importa tipos de la capa de framework; verificado por `templates/check-usecases-no-framework-types.mjs` | que un cambio de framework o de ORM obligue a reescribir la lógica de aplicación |
| El grafo de dependencias entre componentes es acíclico (ADP) | script | `madge --circular` o regla `no-circular` de `dependency-cruiser`; verificado por `templates/check-no-circular-dependencies.mjs` | cambios que se propagan impredeciblemente por un ciclo de dependencias, imposibilitando releases independientes |
| Los repositorios se definen como interfaz en la capa interior; la implementación concreta (SQL, HTTP, etc.) vive en la capa exterior (DIP) | no automatizable | — verificar que la interfaz vive "en el lugar correcto" según su rol arquitectónico exige criterio de diseño, no sólo ubicación de archivo | que la capa interior quede atada a una tecnología concreta de persistencia |
| La lógica de negocio no vive en controladores; el controlador sólo traduce y delega al Use Case | no automatizable | — distinguir "traducción legítima" de "lógica de negocio filtrada" requiere leer el código, ningún regex lo decide con precisión | lógica duplicada entre endpoints y untestable sin levantar HTTP |
| Main (composition root) es el único lugar que instancia clases concretas y las conecta; las capas internas nunca hacen `new` de una implementación concreta | no automatizable | — requiere trazar dónde se instancia cada clase concreta a través de todo el proyecto, análisis semántico fuera del alcance de un linter | construcción de dependencias esparcida por el código, imposibilitando el swap de implementaciones en un solo lugar |
